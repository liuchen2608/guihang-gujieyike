# 第一阶段安全加固与上线检查

本阶段基于 `f102b66` 邀请码版本进行加固。本文描述实现及本地验证，不代表生产环境已经更新。未购买云安全产品，未修改生产凭据、玩家记录或 GitHub 设置。

## 两个版本的身份边界

- `web/` 保留邀请码限制：游客凭服务器保存的邀请授权及 HttpOnly Cookie 访问；GitHub 用户还需要有效邀请授权。请求正文和 URL 中的玩家编号不参与身份判定。
- 新兑换邀请码不再接受 `legacyPlayerId` 认领旧数据。原来已兑换的有效 Cookie 和已绑定账号继续工作。首次兑换前的匿名存档仍在原存储中，不能仅凭一个 UUID 自动迁移。
- `volcengine/` 当前没有邀请码功能，保持原有游客试玩准入。新增 `/api/auth/guest` 签发服务器游客会话；客户端 UUID 不再是凭证。新游客使用单独 `guest:` 命名空间。GitHub 合并必须匹配 OAuth 发起时的原游客 Cookie。
- 浏览器切换身份时保留旧编号和旧存档指针，分别放在 `guihang_legacy_player_id`、`guihang_legacy_save_id`，不删除旧玩家数据。这些标识仅用于联系邀请人恢复，不能直接授权。

旧匿名身份本来没有额外的可靠凭据，无法同时保证“任意旧编号自动续玩”和“禁止冒认”。上线前需通知旧玩家并制定人工核验流程。本阶段没有开放可被滥用的自助 UUID 认领接口，也没有执行旧存档迁移。

## 限流和模型费用

| 项目 | 当前设置 |
| --- | --- |
| 单玩家 AI | 每分钟 8 次、每天 30 次 |
| 单玩家回合请求 | 每分钟 30 次，包括不调用模型的回合 |
| 单玩家新建存档 | 每 10 分钟 3 次 |
| 单玩家反馈 | 每天 3 次 |
| 网络辅助限制 | 回合每分钟 120 次；建档每 10 分钟 30 次；反馈每天 30 次 |
| 火山版游客注册 | 网络每 10 分钟 10 次；全站每天 50 个 |
| 原站新增全站 AI 配额 | 默认每天 50 次、每月 500 次，可用环境配置降低或调整 |
| 火山版全站 AI 配额 | 沿用既有持久化计数和环境值，不重置已经使用的额度 |

计数保存在 D1 / TOS，跨进程、重启均生效；窗口以 UTC 固定时间段计算。多级限制采用保守预扣，后续步骤被拒绝或模型失败也可能占用前一级额度，不承诺只有成功回复才计数。限流返回 429 和 Retry-After；模型不可用或额度耗尽时使用现有本地叙事。

云端入口仍需要网关限流，不能把应用层限流当成 DDoS 防护。原站使用托管边缘的 `CF-Connecting-IP`。火山版默认不信任客户端转发头：没有配置可信头时全部访客共用保守网络额度。仅在确认网关覆写该头、禁止绕过网关访问之后，才设置 `TRUSTED_CLIENT_IP_HEADER`；不要直接信任用户提供的 X-Forwarded-For。

两个站点计数独立。若共用一把模型密钥，需分别分配额度并在供应商侧核验总预算，不能认为一个站点的限额同时覆盖另一个。请求次数不等于人民币硬上限；网关、TOS、函数及流量费用不在此计数范围内。

## AI 紧急开关

将目标环境的服务器变量 `AI_ENABLED` 设置为 `false` 并按平台流程使配置生效，即停止新的付费模型调用；保留读档及本地叙事。恢复时设置为 `true`。未设置时保留现有启用行为，非 true 的异常配置按关闭处理。

本阶段提供的是服务器配置开关，不是公开网页上的管理按钮。不要把云凭据、模型密钥或管理员开关放进客户端。已经发出的上游请求不能保证取消或退费，模型调用本身有 25 秒超时。

## 并发、断线与恢复

- 同一玩家的行动用持久化互斥记录保护；同一存档版本就是一次行动的幂等标识。
- 调用模型之前写入持久化受理记录，重复请求不会重新调用模型。
- 受理记录不因进程重启或网络错误被清除。提交存档前再次检查锁的所有权和期限；保留原有版本条件更新。
- 同一玩家的处理中租约为 5 分钟，过期后可操作其他存档，但同一不确定版本仍不能重新生成。
- 如果模型已经响应但保存结果不确定，先读取存档核对。若版本已经增加，继续下一回合；若仍未增加且受理记录存在，联系邀请人核验日志和上游结果，不能自动重试付费调用。
- 暂时没有自动恢复不确定回合的后台工具。这是故意的保守限制；不要仅按时间清除受理记录或回滚到没有防护的版本。恢复方案应保存/复用已确认结果，或人工确认后进行无模型恢复，并保留审计记录。

## 上线前步骤

1. 先备份实际玩家数据，核对现有邀请配置和旧玩家恢复方式。本次未做生产备份或迁移。
2. 原站新增迁移为 `drizzle/0004_brief_barracuda.sql`，仅新增 `security_records`，不修改旧存档表；应检查并通过原有发布流程执行。运行时初始化也使用同样的非破坏性建表逻辑。
3. 火山版新增记录位于业务前缀下的 `security/`，确认专用账号具备该前缀的读写权限。保持业务桶版本控制关闭，不把安全加固当作开启版本控制的理由。
4. 核对两个环境的全站模型额度和 `AI_ENABLED`；不把本地示例变量当作已经配置生产。
5. 测试环境验证：现有邀请游客续玩、账号恢复、没有 Cookie 的伪造编号拒绝、新兑换不认领旧编号、并发只执行一次、额度重启后仍有效、AI 关闭后的本地叙事。
6. 确认旧玩家影响和访问范围后再发布；发布后做小流量验收，避免直接进行线上压力测试。

## 验证与剩余范围

运行各目录的 `npm test`、`npm run lint`、TypeScript 检查与 `npm run build`。原站额外使用真实路由及 SQLite 的隔离集成测试，模型接口为测试替身，不消耗真实模型费用；火山版有会话、TOS 适配器、并发和额度回归测试。原站开发环境最低 Node.js 更新为 22.16（测试使用模块钩子及 SQLite 列信息接口），本轮在 Node.js 24.19.0 验证；没有升级业务依赖。

下一阶段仍包括：RAG 章节权限进一步细化、独立自动备份和恢复演练、云端告警/WAF、GitHub 账户双重验证与仓库保护设置、旧存档的人工核验工具。它们没有因为本阶段代码完成而自动上线。
